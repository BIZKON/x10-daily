## 2. Отклонения от плана (каждое обосновано в коде)

1. **Промпт по канону `visual.md`, а не по черновику плана.** Черновик просил
   `subtle glow` и тёмный charcoal-фон — канон это прямо запрещает («не использует
   неон, киберпанк, AI-свечение»; палитра приглушённая, золото только как тонкий
   хром). Порядок блоков канонический: STYLE → PILLAR → SUBJECT → NEGATIVE → TECH.
   NEGATIVE дописывается ПОСЛЕ сцены — модель-крафтер не может протащить в кадр
   текст, лицо или логотип.
2. **Генерация и запись — ОДИН Inngest-шаг** (в плане были раздельные `generate` и
   `store`). Inngest сериализует результаты `step.run` в JSON: ~450–800 КБ байтов
   картинки через границу шага распухли бы в `{"0":255,…}` и упёрлись в лимит вывода.
   Наружу отдаётся только публичный URL. Плата — ретрай перегенерирует картинку
   (`retries:1` → максимум два вызова модели).
3. **URL обложки несёт версию содержимого** `?v=<хеш байтов>`. Имя файла
   детерминировано по `articleId`, перегенерация ПЕРЕЗАПИСЫВАЕТ тот же путь — с
   `immutable`+1год из плана новая картинка навсегда осталась бы невидимой.
4. **Экран админки — `/visuals`**, не `(dash)/visuals`: такой группы маршрутов в
   админке нет (маршруты плоские).
5. **Сверх плана — гейт `visual_status` в API ленты.** Без него отклонённая
   редактором («без картинки») или ещё не отсмотренная ИИ-обложка всё равно
   показывалась бы в ленте Mini App — дыра в HumanGate. Теперь лента отдаёт
   `coverImageUrl` только при статусе `approved` или `none` (`none` = ручная/легаси
   обложка, к ИИ-генерации отношения не имеет).

## 3. Как это работает (контур целиком)

```
draft-article ──persist──▶ событие article/cover.requested
                                    │
                            generate-cover (Inngest)
                    load-article → visual-prompt (VisualAgent, DeepSeek РФ)
                    → generate-and-store (Nano Banana 2 → JPEG → том covers)
                    → visual_status = 'pending_review'        🔴 НИКОГДА не approved
                                    │
                        админка /visuals — решение редактора
              одобрить → approved │ без картинки → rejected │ перегенерить → force
                                    │
   drain-post-slots (слоты 4/день): approved + есть URL → sendPhoto + подпись ≤1024
                                     иначе               → текстовый пост, как раньше
```

**Фолбэк железный:** любой сбой (шлюз, диск, агент) → `visual_status` не становится
`pending_review` → канал постит текстом, лента показывает `BrandedCover`.

**Выключатель:** пустой `COVERS_PUBLIC_BASE_URL` → `generate-cover` скипается с
причиной `covers-disabled`, поведение прода ровно как до сессии.

## 3а. Адверс-ревью перед деплоем (Workflow `wr7yj18a6`)

6 линз → 39 агентов, каждая находка проходила отдельного агента-опровергателя.
**32 вердикта, 15 подтверждено, 13 записей схлопнулись в 7 уникальных причин.**

**Два блокера — оба ПОЧИНЕНЫ до деплоя:**

- 🔴 **Б1 (живой канал).** `sendPhoto` с HTTP 400 по САМОЙ картинке (Telegram не
  смог скачать URL / `IMAGE_PROCESS_FAILED`) не деградировал в текст: фолбэк слал
  ту же картинку, финальный вызов не был обёрнут в try/catch, бросок уходил из
  шага. Слот терялся целиком, `recordChannelFailure` не вызывался (нет ни
  `attempts`, ни `last_error`), а выборка FIFO брала ту же строку каждым
  следующим слотом в пределах `STALE_HOURS=24` — **до четырёх молчащих слотов
  подряд**. Это была регрессия относительно текущего прода, где фото-ветка была
  мёртвой. Фикс: цепочка деградации фото-HTML → фото-plain → rich-HTML текстом →
  плоский текст, и текстовый пост строится ВСЕГДА, а не только когда обложки нет.
- 🔴 **Б2 (HumanGate).** Гейт `visual_status` я поставил в ленте, но **не в
  читалке** — а именно туда ведёт deep-link из каждого поста канала. Неодобренная
  обложка была бы видна каждому читателю hero-баннером, а отклонённая («без
  картинки») — навсегда, потому что `reject` не обнуляет `cover_image_url`.
  Фикс: `gateCoverByVisualStatus` в `apps/api/src/routes/articles.ts`, покрыт
  тестами на все пять статусов.

**Два MED тоже закрыты сразу** (лежат в пути живого канала):
`«Перегенерировать»` снимает одобрение (`generating`) ДО генерации — иначе
перезапись файла по тому же пути обесценивала одобренные байты, и слот мог
отправить в канал непросмотренную картинку; `Cache-Control: immutable` больше не
вешается на 404 (матчер `@exists`) — иначе клиент закэшировал бы «нет картинки»
на год в окно первого включения.

**Осталось незакрытым (не блокер):** при броске шага отправки
`recordChannelFailure` не вызывается → в `channels` нет диагностического следа
(`attempts`/`last_error`). После Б1 бросок стал маловероятным, но след полезен.

## 4. Грабли сессии (переиспользуемо)

- **Inngest json-ит результаты `step.run`** — бинарные данные через границу шага возить нельзя.
- **Лимит caption Telegram (1024) считается ПОСЛЕ разбора сущностей**: теги не входят,
  `&amp;` = один символ. Резать надо по видимой длине, иначе либо теряешь место, либо ловишь 400.
- **`escapeTelegramHtml` не экранирует кавычку** — для значения атрибута `href` этого мало,
  URL с `"` разорвал бы атрибут (в `caption.ts` добавлено отдельное экранирование).
- **PPR в админке:** страница, чей data-fetch выходит раньше обращения к `cookies()`
  (на билде `X10_API_BASE_URL` не задан), собирается как `○ Static` и запекает
  «Данные недоступны» навсегда. Диагностика: `postponed` в `.next/server/app/<route>.meta`.
  Лечится `connection()` внутри Suspense-компонента.
- **`handle`-блоки Caddyfile срабатывают в порядке записи** — `handle_path /covers/*`
  обязан стоять ДО общего `handle`.
- `caddy validate` можно прогнать на VM по временному пути, не трогая живой конфиг.
- В контейнере `api` нет пакета `pg` — прод-SQL гонять одноразовым `postgres:17-alpine`
  с `-f файл.sql` (кавычки в `node -e` через ssh не выживают).
- Вывод `console.log` в vitest подавляется — печатать в файл.
