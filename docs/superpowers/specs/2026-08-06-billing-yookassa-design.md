# Спека 6 — Баланс клиента, оплата через ЮKassa и остановка по нулю

**Дата:** 2026-08-06 · **Статус:** шаги 1–2 из 7 построены (07.08.2026), шаги 3–7 впереди
**Приоритет:** 🔴 **ВАЖНО** — без этого контент-завод нельзя продавать: токены
оплачиваем мы, а получить деньги обратно нечем.
**Смежное:** Спека 5 (роли и права), скилл `yookassa-timeweb-payments` (грабли
интеграции), `docs/BACKLOG.md` (открытые пункты по деньгам).

## 1. Откуда взялась задача

Утром 06.08.2026 решили: каждый клиент получает отдельную копию системы.
Вечером уточнили модель денег: **токены оплачиваем МЫ, клиент платит нам по
нашему тарифу — себестоимость ×3**.

Сейчас в системе есть только половина: рублёвая себестоимость каждого прогона
фиксируется в `pipeline_runs.cost_rub`, а экран «Расходы» показывает рядом
цену клиенту. **Денег с клиента получить нечем и остановить работу при
неоплате нечем.** Эта спека закрывает обе дыры.

## 2. Решения владельца (зафиксированы 06.08.2026)

| Вопрос | Решение |
|---|---|
| Модель оплаты | **Предоплата**: клиент кладёт на баланс, мы списываем по факту ×3 |
| Что при нуле | **Стоп конвейера** + предупреждение заранее |
| Чеки 54-ФЗ | **ЮKassa сама** (облачная касса), `receipt` в каждом платеже |
| Где пополняет | **В кабинете**, раздел «Расходы» |

Почему предоплата, а не постоплата: при постоплате мы месяц финансируем чужие
токены своими деньгами и несём риск неплатежа. Предоплата — то же, что клиент
уже понимает по опыту любого рекламного кабинета.

## 3. Что появляется

### 3.1 Баланс экземпляра

Одна запись на копию системы — `tenant_id` по-прежнему не вводим (решение
06.08). Таблица `client_balance`:

| Поле | Зачем |
|---|---|
| `balance_rub` | остаток. Уменьшается при каждом прогоне |
| `low_threshold_rub` | ниже — предупреждаем. По умолчанию 500 ₽ |
| `updated_at` | когда двигали последний раз |

🔴 **Баланс двигается только условным UPDATE** (`balance_rub = balance_rub - X`),
никогда чтением-в-код-и-записью. Между чтением и записью успевает второй прогон,
и остаток разъедется с реальностью — на деньгах это недопустимо.

### 3.2 Журнал движений

`balance_entries` — почему остаток именно такой. Без журнала спор с клиентом
неразрешим.

| Поле | Зачем |
|---|---|
| `kind` | `topup` (пополнение) · `charge` (списание) · `adjust` (ручная правка) |
| `amount_rub` | со знаком: пополнение плюс, списание минус |
| `balance_after_rub` | остаток ПОСЛЕ операции — чтобы не пересчитывать историю |
| `run_id` | ссылка на `pipeline_runs` для списаний |
| `payment_id` | ссылка на платёж для пополнений |
| `note` | человеческое пояснение для `adjust` |

### 3.3 Платежи

`payments` — то, что ЮKassa знает о наших деньгах.

| Поле | Зачем |
|---|---|
| `provider_payment_id` | id платежа в ЮKassa, **UNIQUE** — на нём стоит идемпотентность |
| `amount_rub`, `status` | `pending` · `succeeded` · `canceled` |
| `created_by` | кто нажал «Пополнить» |
| `credited_at` | когда зачислили на баланс. NULL = ещё нет |

🔴 **Зачисление ровно один раз.** ЮKassa повторяет уведомление, пока не получит
200, и присылает его не по одному разу. Зачисление идёт условным UPDATE по
`credited_at IS NULL` — второе уведомление не добавит денег.

## 4. Списание

Списываем там же, где уже пишем себестоимость — в `recordRun` (`cost-ledger.ts`).
Одна транзакция: строка в `pipeline_runs` + движение в `balance_entries` +
уменьшение `client_balance`.

Сумма списания = `cost_rub × CLIENT_PRICE_MULTIPLIER`.

⚠️ Наценка сейчас константа кода. Для продажи разным клиентам по разным тарифам
её придётся вынести в настройку экземпляра — записано в §8.

## 5. Остановка по нулю

Гейт встаёт рядом с существующим дневным потолком (`isPostingPaused` и проверка
бюджета в конвейере) — то есть в одном месте, а не в каждой функции.

- `balance_rub <= 0` → конвейер не берёт новую работу. Уже начатое доделывается:
  бросать материал на полпути дороже, чем доработать в минус на копейки.
- `balance_rub < low_threshold_rub` → предупреждение **один раз в сутки** в
  группу «Редакция» и плашка в кабинете. Каждый прогон слать нельзя: клиент
  отключит уведомления и не увидит настоящую остановку.
- Остановка **не касается уже одобренного** к публикации: заплаченное должно
  выйти.

## 6. Пополнение

1. Клиент в разделе «Расходы» жмёт «Пополнить», выбирает сумму.
2. `POST /v1/admin/billing/topup` — право `cost.view` (кто видит суммы, тот и
   платит). Создаёт строку `payments` и платёж в ЮKassa.
3. Редирект 303 на `confirmation.confirmation_url`.
4. Клиент платит, возвращается на `return_url` → `/cost?payment=<id>`.
5. ЮKassa шлёт `payment.succeeded` на **публичный** `POST /v1/billing/yookassa`.

### Что обязательно по скиллу `yookassa-timeweb-payments`

- Авторизация — Basic `base64(shopId:secretKey)`, заголовок `Idempotence-Key`
  на создании платежа (годится id нашей строки `payments`).
- Вебхук **перепроверяет платёж** через `GET /v3/payments/{id}` и не верит телу
  уведомления. Зачисляем только при `status=succeeded && paid`.
- Вебхук **всегда отвечает 200**, даже на мусор: иначе ЮKassa будет ретраить.
- Вебхук публичный — без сессии и CSRF, но с проверкой, что платёж наш
  (`provider_payment_id` есть в нашей таблице).
- `amount.value` — строка с двумя знаками («1000.00»).
- ⚠️ **CSP `form-action`** режет редирект на `yoomoney.ru` молча: прямая ссылка
  открывается, кнопка — нет. У нас CSP сейчас **не выставляется** (проверено на
  проде 06.08.2026), но при его появлении домены ЮKassa надо внести сразу.

## 7. Что видит клиент

Раздел «Расходы» дополняется сверху:

- **Остаток** крупно, рядом «хватит примерно на N дней» по среднему расходу.
- **Пополнить** — кнопка с готовыми номиналами.
- **Движения** — последние списания и пополнения из `balance_entries`.

Себестоимость клиенту не показываем: он видит цену по своему тарифу. Разбивка
«ушло на обложки / на тексты» — в его ценах.

⚠️ В НАШЕЙ копии владелец видит и себестоимость, и цену — это уже сделано.

- Счета для юрлиц и закрывающие документы.
- Разные тарифы разным клиентам: наценка пока константа кода.
- Мультивалютность.

## 9-бис. Решения, принятые при постройке шага 1 (07.08.2026)

Этих вопросов в дизайне не было — всплыли на реализации.

### За что клиент платит, а что мы едим сами

Списываем за прогоны со статусом `succeeded`, `skipped` и `halted`. **`failed`
не выставляется клиенту.**

- `skipped` — гейт отбраковал сырьё. Это не брак, а работа фильтра: отделить
  подходящее от неподходящего можно только прочитав всё.
- `halted` — FactCheck остановил материал из-за расхождения источников. Тоже
  услуга: клиента уберегли от публикации непроверенного.
- `failed` — наша авария. Клиент не получил ничего, а ретраи умножили бы сумму.
  Себестоимость остаётся на нас и видна в `pipeline_runs` как расход без
  списания.

Меняется одним списком `BILLABLE_STATUSES` в `cost-ledger.ts`.

### Флаг `client_balance.billing_enforced`

Заведён на шаге 1 как `stop_on_zero`, на шаге 2 **переименован** (миграция 0021):
он управляет не только остановкой, но и предупреждениями. У клиента остановка по
нулю нужна (дефолт `true`), а **наша собственная копия платит шлюзу напрямую и
сама себе ничего не переводит** — её остаток уходит в минус и должен уходить. С
прежним смыслом она получала бы ежедневное ложное «деньги кончились», а это
способ научить людей не читать тревоги. В нашей строке `false`; минус показывает
накопленную стоимость нашего контента в клиентских ценах — по нему и проверяется,
сходится ли расчёт.

### Списание живёт в одной транзакции с прогоном

Списание без причины неоспоримо, причина без списания тихо теряет деньги —
поэтому строка `pipeline_runs`, движение остатка и запись в `balance_entries`
пишутся одной транзакцией. Обратная сторона: сбой в денежной части откатит и
строку прогона. Пошли на это сознательно; `deploy.sh` применяет миграции до
подъёма контейнеров, поэтому «таблицы ещё нет» в нормальном цикле не случается.

### Мелочи, которые стоило зафиксировать

- `balance_entries.run_id` — **ON DELETE SET NULL**, а не CASCADE: `pipeline_runs`
  удаляются вместе со статьёй, и при CASCADE удаление статьи стирало бы запись о
  деньгах.
- Синглтон баланса держится типом ключа (`id boolean CHECK (id)`), а не
  договорённостью — второй строки не появится даже при вставке руками.
- Остаток двигается upsert'ом: если строки баланса нет, она создаётся тем же
  запросом, и списание не теряется молча.

## 11. Шаг 2 — как сделана остановка (07.08.2026)

### Где стоит гейт

Политика — одной чистой функцией `decideBillingState` в
`apps/workers/pipeline/src/lib/billing-gate.ts`; спрашивают её четыре платные
функции: `process-source-item`, `draft-article`, `generate-cover`,
`rewrite-article`.

Гейт стоит **на входе** каждой, до вызова модели. Одного места «где-то в
середине» не бывает: деньги тратит каждая из них по отдельности, и проверять
надо там, где начинается трата. Общая у них политика, а не точка вызова.

🔴 `drain-post-slots` НЕ гейтится намеренно: одобренное к публикации уже
оплачено при подготовке. Останавливать выход заплаченного — значит брать деньги
и не отдавать работу.

⚠️ Дешёвый гейт источников (`process-source-item`) раньше продолжал работать при
исчерпании НАШЕГО дневного потолка — это правильно, потолок про нас. Но при
пустом балансе КЛИЕНТА он останавливается: он идёт на каждый item каждые пять
минут, и без остановки мы месяцами оплачивали бы чужие ленты из своего кармана.

### Куда уходит предупреждение

🔴 **В группу «Редакция» клиента (`TG_REVIEW_CHAT_ID`), а не в наш служебный
чат.** До шага 2 все алерты шли только нам — то есть клиент, у которого встал
конвейер, узнавал бы об этом от нас или не узнавал вовсе.

Маршрут определяется **видом** алерта (`sendByKind`), а не местом вызова. Иначе
дослыка (`retry-ops-alerts`) отправила бы клиентское предупреждение нам: она
видит только строку в очереди. Ради этого `PendingAlert` теперь несёт `kind`.

Молчаливого запасного адреса нет: если группа не настроена, строка остаётся в
очереди дослыки (её подберёт sweeper, когда адрес появится). Отправить
предупреждение о чужих деньгах туда, где клиент его не увидит, — хуже, чем
задержать.

### Идемпотентность

Переиспользован `cost_alerts`: там уже есть «один алерт на (день, вид)» и очередь
дослыки. Новые виды `balance_low` / `balance_empty` добавлены **отдельной**
миграцией 0022 — PostgreSQL запрещает использовать новое значение enum в
транзакции его добавления.

⚠️ `cost_alerts.spend_usd` для этих видов пишется `0`: колонка про долларовый
расход дня, к остатку она отношения не имеет. Суммы живут в тексте алерта.

### Что видит клиент в кабинете

Плашка на всех страницах (`BillingBanner` в раскладке админки, ручка
`GET /v1/admin/billing/balance`). Отвечает на вопрос «почему ничего не
готовится»: без неё остановка выглядит поломкой.

- Доступна **всей команде** — автор, увидевший пустую очередь, должен понимать
  причину, а не идти выяснять её у владельца.
- **Суммы** — только тем, кому дано `cost.view`; остальные видят факт без цифр.
- Молчит, когда контур выключен, денег хватает или ответа от сервера нет:
  плашка, появившаяся из-за сетевого сбоя, пугала бы зря.

🔴 PPR: плашка живёт в своём `Suspense` с `connection()`. Без этого статичные
страницы запекли бы ответ, полученный на сборке («плашки нет»), и клиент никогда
не узнал бы об остановке. Проверено ключом `postponed` в `.next/server/app/*.meta`.

### Отказоустойчивость

Денежный контур не должен становиться новой причиной падения завода:

- баланс не прочитался → работаем (неизвестное состояние не повод глушить
  чужой завод);
- предупреждение не отправилось → остановка всё равно в силе (она про деньги, а
  не про то, дошло ли сообщение);
- оценка «хватит на N дней» не посчиталась → предупреждение уходит без неё.

### Что нашла репетиция на проде (07.08.2026)

Контур включили на несколько минут с ПОЛОЖИТЕЛЬНЫМ остатком ниже порога —
сработало только предупреждение, без остановки. Оно ушло в «Редакцию» и
доставилось с первой попытки, конвейер продолжал работать.

🔴 **И текст соврал:** «осталось 300 ₽ — примерно на 3080 дней». Средний расход
делился на полную длину окна (7 суток) независимо от того, сколько данных реально
накопилось, а накопилось два часа. У нового клиента истории всегда мало, поэтому
так выглядела бы вся его первая неделя — и остановка стала бы полной
неожиданностью, то есть ровно тем, что предупреждение обязано предотвращать.
